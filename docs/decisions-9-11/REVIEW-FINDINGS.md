# Review findings — planning zip vs. decisions 9–11

Gaps, contradictions and impossibilities found in `horeca-planning-final.zip` while making decisions 9–11.
**Nothing in the planning zip was edited** (handoff rule 3). Each finding has a proposed change for Member A.
Severity: 🔴 must fix before the spec is approved (G1) · 🟠 fix in the affected task · 🟢 wording / docs.

| # | Sev. | Where | Finding | Proposed change |
|---|---|---|---|---|
| F1 | 🔴 | HANDOFF 11.7 vs README "What it does", CLAUDE.md "Project", README "Known limitations" | **Two different money models.** README/CLAUDE.md: the platform "records what each supplier is owed" and "holding third-party funds is a regulated activity" → buyers pay the **platform**. HANDOFF 11.7 "earlier recommendation": one pro-forma per sub-order "with the supplier's details and IBAN" → buyers pay **suppliers**, and then the platform owes suppliers nothing. Both cannot be true. | Decision 11.7: **one pro-forma per order, issued by the platform, paid to the platform's account**; suppliers appear as sections. Keeps the ledger meaning, the project brief and "check out once". Replace the HANDOFF sentence in the spec. |
| F2 | 🔴 | CLAUDE.md → Testing rules; TASKS D11-B2 | Invariant **"payable + commission = sub-order net"** is wrong for the chosen model: the buyer pays the gross amount to the platform and the VAT belongs to the supplier, so the platform must pass it on. | Change to **"payable + commission = sub-order gross"** (money-rules.md §3). Commission stays on the **net**. |
| F3 | 🔴 | README features, DESIGN screens, TASKS | **Nobody records that a pro-forma was paid.** "Settled by invoice" needs a place to record the buyer's bank transfer (and refunds after a cancellation). | Added `order_payments` (receipt / refund, append-only) + derived `orders.payment_status`. Needs an admin screen "Record payment / refund" (≈ 0.5 d A, e.g. in D13-A2) and a domain action (≈ 0.5 d B, D11). Payment status is informational in the MVP (open question Q3). |
| F4 | 🟠 | DESIGN.md → Documents ("Generated once … never regenerates it") + TASKS D12/D13 | A sub-order can be cancelled **after** the pro-forma was issued; the stored PDF would then show a wrong total. | Never regenerate a file — **issue a new version** (`PF-2026-000123/2`) by a job after the cancellation commits; the old one becomes `superseded`. Add the re-issue job to D12-B1 or D13-B1. |
| F5 | 🟠 | Planning matrix "Download pro-forma: supplier own" | With one pro-forma per order (F1), the document lists **other suppliers' lines and prices** → information leak between suppliers. | Supplier: **no access** to the pro-forma; it sees its sub-order detail (and the copy of the payment status). Applied in permission-matrix.md ✏️. |
| F6 | 🟠 | README env table, `.env.example`, TASKS D4-B2 ("Two database roles") | The system context for worker jobs needs its own credentials so a web request can never obtain it (decision 9.4). | **Three** roles: `horeca_owner` (migrate), `horeca_app` (web), `horeca_worker` (worker). New env var **`DATABASE_WORKER_URL`** (worker container only). Update D4-B2, README env table, compose files. |
| F7 | 🟠 | TASKS D9-B1 vs D11-B1 | D11-B1 says ledger entries are "written in the checkout transaction", but the checkout is built on D9. The RLS policy allows `sale`/`commission` inserts only while the sub-order is `pending`, i.e. at checkout. | Either write the two entries already in D9-B1 (preferred — one checkout transaction, one PR), or let D11-B1 extend `createOrder`. Note it in TASKS. |
| F8 | 🟠 | `docs/diagrams/erd-identity.mmd` | Columns adjusted by decisions 9/11: `supplier_profiles.commission_override` → **`commission_override_bps integer`**; `org_profiles` gets `city`, `postal_code`, `country`, `rejection_reason`, `status_changed_at/by`, timestamps (address split for invoices); `buyer_locations` gets `city`, `postal_code`, `country`, `contact_name/phone`, `is_default`, `archived_at`; `audit_log` final columns (`actor_org_type`, `entity_type`, `entity_id`, `before`, `after`, `request_id`). | Update the identity ERD from `schema/identity-ext.ts` and `schema/finance.ts`. |
| F9 | 🟠 | Decision 3 ("checkout must reject buyer and supplier sharing a tax ID") | Enforced in the checkout revalidation (domain). The database can only guarantee `buyer_org_id <> supplier_org_id` (CHECK on `sub_orders`), not "different tax ID", because the tax ID lives in another table. | Keep it in the domain + a checkout test; documented in decision 11.8. No change needed beyond the test in D9-B2. |
| F10 | 🟢 | DESIGN.md status badges | Sub-order states confirmed unchanged by decision 11. Missing: badge for the **order payment status** (`unpaid` warning · `paid` success · `refund_due` danger) and for the pro-forma version (`superseded` muted). | Add the two rows. |
| F11 | 🟢 | DESIGN "Admin commission" KPI tiles | "GMV net" and "commission earned" need a definition so the tiles match the table. | Use money-rules.md §4: commission per supplier = Σ commission of non-cancelled sub-orders; "earned" = delivered only; both from the ledger. |
| F12 | 🟢 | README "Known limitations" | Two new honest limitations. | Add: "VAT on the platform commission is not modelled" and "Shipping does not wait for payment (payment status is informational)". |
| F13 | 🟢 | README / spec — catalogue filters | With S1, buyer-specific prices are **not** filterable/sortable (Meilisearch holds the base price only). | State it next to the price filter. |
| F14 | 🟢 | Status rules | Buyers can never be suspended (`org_profiles` CHECK keeps buyers `approved`). Fine for the MVP; abuse handling would need it. | Open question Q6; no change now. |
