## 6.1 Entity-relationship diagram

One checkout creates **one `orders` row → one `sub_orders` row per supplier → `order_lines`** (snapshots). Every
order-side table carries `buyer_org_id` and `supplier_org_id` (denormalised on purpose), so each security policy
is a one-column comparison and a supplier never reads the buyer's `orders` row (decision 9.5).

## 6.2 Entity descriptions

Owner = which organization type owns the rows. RLS = who may read / write under Postgres row-level security
(second line of defence; the domain layer's `policy.can` is the first, see [permissions.md](permissions.md)).
**P** = platform admin, **B** = buyer, **S** = supplier, **W** = the worker's database login.

### Identity (Better Auth + our extension)
| Table | Purpose | Owner | RLS (summary) | Key rules |
|---|---|---|---|---|
| `user`, `session`, `account`, `verification`, `organization`, `member`, `invitation` | users, sessions, companies, memberships — **generated by Better Auth's CLI** | — | **none** (library-managed; the app layer protects them, `/organization/*` endpoints are an allowlist) | `organization` is created only by buyer registration or by the admin's "Create supplier" |
| `org_profiles` | the company record: type, status, legal name, tax ID (PIB), address | B, S, P | own row; approved suppliers readable by every logged-in org; P all | tax ID 8 or 13 digits; unique per (tax ID, type); `type` immutable; status change only by P; suppliers are inserted by P **as `approved`** (012) |
| `supplier_profiles` | IBAN, commission override (bps) | S | own (IBAN: owner role only, in the domain); P all | override `0…10000` bps, writable by P only; **insert by P only** (012) |
| `buyer_locations` | delivery addresses | B | own buyer; P read | at most one default per org; archived, never deleted |

### Catalogue (migration 0003 = D3-B2)
| Table | Purpose | Owner | RLS (summary) | Key rules |
|---|---|---|---|---|
| `categories` | tree (depth ≤ 3) stored as `ltree` | P | read: logged-in; write: P | unique slug and path |
| `category_attributes` | typed attribute definitions, inherited down the tree | P | read: logged-in; write: P | key format; enum needs options; min/max for numbers only |
| `products` | supplier-owned listings; attribute **values** as JSONB | S | own; others read `active` rows of `approved` suppliers; P; W read | SKU unique per supplier; price > 0; VAT 0…10000 bps; min order qty is a multiple of the order step; GTIN 8 or 12–14 digits. **No trigram index** (search is Meilisearch) |
| `product_images` | image records; the job writes 3 WebP sizes (320 / 640 / 1280 px) found by convention, `<image id>/<width>.webp` | S | same visibility as the product; W may update `status`, `width`, `height` | ≤ 8 per product, ≤ 5 MB, JPEG/PNG/WebP; **no `thumb_key`** |
| `csv_imports` | import run, status, validation report | S | own; P read | ≤ 5000 rows; one active import per supplier (unique index) |
| `product_stock` *(D5-B0)* | cached stock from the supplier API: `available_qty`, `status` ok/unknown, `fetched_at` | S (data), W (writer) | read: logged-in; written by W only | refreshed every 5 min by a job; shown as a badge |

### Orders and contracts (D4-B1 order core, D5-B0 second migration)
| Table | Purpose | Owner | RLS (summary) | Key rules |
|---|---|---|---|---|
| `carts`, `cart_items` | one cart per buyer **organization**, shared by its members | B | own buyer | product once per cart; `unit_price_cents_seen` drives "price changed" |
| `orders` | one checkout; totals = Σ sub-orders, **never changed afterwards** | B | buyer own; P; W read; no UPDATE grant (status fields come from `app.recompute_order()`) | unique idempotency key **per buyer org**; `payment_status` = `unpaid / paid / refund_due / not_applicable`; **no `payment_method`** (012) |
| `sub_orders` | the supplier's part, with its own status and **purchase mode** | B + S | buyer / supplier / P; money columns immutable (column grant on `status`, `cancel_*`) | `mode` = `direct \| platform` (**012**); `direct` only if the contract is `active` when the checkout transaction runs; `supplier_submission` = `pending / accepted / rejected / failed`, written by W only; commission rate **snapshotted** |
| `order_lines` | snapshot of product name, SKU, unit price, VAT rate | B + S | same as `sub_orders`; insert at checkout only | line net = unit price × qty; gross = net + VAT |
| `sub_order_events` | history of every state transition | B + S | same; insert-only | insert must match the current status |
| `proforma_invoices` | pro-forma for the **platform part** of an order, created once at checkout | B | buyer / P; W renders the PDF (`status`, `storage_key`, `pdf_generated_at`) | totals = platform sub-orders only; number from a **normal sequence** `PF-<year>-<6 digits>` (gaps allowed); `version` stays 1; **suppliers have no access**; none if the order has no platform part |
| `order_payments` | receipts / refunds against an order | B (read) | buyer read; P insert; **W insert** `receipt` / `refund` with a `payment_id` only | insert-only; the manual "record buyer payment" screen is gone (012) |
| `supplier_agreements` *(D5-B0)* | buyer–supplier **contract**: `requested → active \| rejected`, `active → ended` | B + S | own buyer or own supplier; P read | at most one `requested` or `active` row per (buyer, supplier); buyer inserts only `requested`; the supplier decides |
| `payments`, `payment_events` *(D5-B0)* | card payment attempts and gateway events (mock gateway) | B (read), W (writes) | buyer read; W writes; P read | `created → pending → succeeded \| failed \| cancelled \| expired`; at most one `succeeded` per order; `refunded_cents` ≤ amount; duplicate gateway event ID = no-op; **no card data anywhere** |

## 6.3 Data validation rules

**Three layers, and each one is enough on its own to stop bad data.**
1. **Zod at every boundary** (`src/lib/schemas`): forms, Server Actions, route handlers, job payloads. Unknown
   keys are rejected, request input is never spread into an insert (no mass assignment). Attribute schemas are
   *generated* from `category_attributes`.
2. **Domain layer:** status preconditions, quantity rules, revalidation inside the checkout transaction.
3. **Database:** `CHECK` constraints, unique indexes, foreign keys, RLS and guard triggers — they hold even if a query forgets a filter.

| Rule | Where |
|---|---|
| Money is integer **cents** (`bigint`), rates in **basis points** (`integer`); no floats | column types, `money.ts` |
| `gross = net + VAT` on lines, sub-orders and orders; `0 ≤ commission ≤ sub-order net`; commission bps `0…10000` | `CHECK` |
| Tax ID (PIB): 8 or 13 digits; unique per (tax ID, type); buyer tax ID ≠ supplier tax ID at checkout | `CHECK`, unique index, checkout revalidation |
| SKU unique per supplier; GTIN 8 or 12–14 digits | unique index, `CHECK` |
| Quantity ≥ minimum **and** a multiple of the order step — on adding to the cart and again at checkout | Zod, domain |
| Images ≤ 5 MB, type by **magic bytes**, ≤ 8 per product, random stored file names | upload route handler, `CHECK` |
| CSV: ≤ 5000 rows, one leaf category per file, validate → confirm, upsert by (supplier, SKU), one active import per supplier | job, unique index |
| Idempotent checkout: same key + same request = the existing order, same key + different request = validation error | `orders` unique index, domain |
| `direct` mode only under an `active` contract; `sale` is never booked for a direct sub-order | domain **and** RLS insert policies |
| Ledger and audit log are append-only; a correction is a new entry | no UPDATE / DELETE privilege |
| A sub-order's money columns cannot change after checkout | column grant (`horeca_app` may update only `status`, `cancel_reason`, `cancelled_by_user_id`, `status_changed_at`) |
| No card data in the app, database or logs | design rule; only the mock gateway's hosted page sees a card number |

Errors: invalid input → `Validation` (422 + field errors); a wrong-status action → `Conflict` (409). User-facing
messages are Montenegrin (decision 012 §10) and come from message catalogues, not from the domain code.
